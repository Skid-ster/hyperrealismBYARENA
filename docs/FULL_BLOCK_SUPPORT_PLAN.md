# Full Minecraft block support and pack-specific shader assessment

## What “full block support” means

The target is every vanilla Minecraft Java 26.3 blockstate and every texture it
references, including face-specific textures, particles, connected-glass support,
cutout silhouettes, animated frames, emissive parts and state-dependent models.
The generated pack must leave vanilla blockstates, models, UVs, geometry and
behavior intact unless a narrowly scoped, tested compatibility feature requires
otherwise. This is not a promise to replace item, entity, GUI, sky or other
non-block assets; those need separate scope and audits.

A block is not necessarily one texture. A door, crop, bed, command block,
rotatable log, pane or animated block can depend on multiple sprites, rotations,
alpha shapes, variants or metadata. “One generated image per block” would be
incorrect. The canonical unit of coverage is a resource texture path, with an
explicit mapping back to every state/model that uses it.

## Baseline audit (26.3 metadata only)

`catalog/vanilla_26.3_full_block_coverage.json` is generated by
`scripts/audit_full_block_coverage.py` from the pinned metadata mirror
`InventivetalentDev/minecraft-assets` at commit
`6c088630459d8ca369ef0d6c07636d7d63a3b0f1`. It walks blockstate variants and
multipart models, follows model parents and texture variables, and records
resource names only. No Minecraft image data is copied or committed.

The current audit reports:

- 1,290 blockstate JSON files and 2,885 block-model JSON files.
- 1,272 distinct `minecraft:block/*` texture references.
- 352 referenced paths are covered by the material manifest; 920 remain
  uncovered.
- 611 blockstates currently have at least one uncovered referenced texture.
- The pinned-metadata resolver reports zero unresolved texture variables and
  zero block texture paths unrelated to any blockstate.

The latest incremental additions are five copper paths (copper block, cut
copper and its three oxidation-stage variants) plus raw copper, gold and iron
blocks. They use verified CC0 Poly Haven scans already in the project: Metal
Plate 02/Rusted Shutter for the copper surfaces and Rock Face 03 for ore-host
rock. Cut copper uses a deterministic 4×4 panel-and-recess recipe; raw blocks
use the ore-inclusion recipe. Target colors are alpha-weighted averages computed
locally from pinned reference textures; no Minecraft image pixels are included
in the pack or repository. Recipe periodicity and coverage are tested. This is
structural coverage progress, not in-game visual validation.

This establishes that the current source catalog is still a subset, not full
block coverage. These counts describe the pinned asset mirror's metadata, not a
live client-JAR validation or proof of visual correctness. The audit still needs
to be rerun against the exact 26.3 client JAR used for a release before claiming
version-complete support.

Rebuild the catalog after preparing a local metadata checkout (only JSON
metadata is needed):

```sh
python3 scripts/audit_full_block_coverage.py --assets PATH_TO_ASSET_CHECKOUT
```

The default manifest and output paths are repository-relative. The upstream
mirror is an audit source, not a source of artwork or a substitute for licensed
photographic material.

## Roadmap and acceptance gates

1. **Close the inventory contract.** Resolve all parent, variable, particle,
   special-model and texture-path cases. Check every resolved path exists in the
   pinned client metadata, define animation/cutout/mipmap/CTM handling, and make
   missing, unsupported and intentionally vanilla-fallback paths separate
   machine-readable statuses. Add reproducible coverage checks for every
   blockstate, not a hand-selected sample.
2. **Build material families, not 920 unrelated recipes.** Group semantically
   related block paths into defensible families (stone/ore, soil/sand, wood/bark,
   masonry, metal, glass, foliage/crops, Nether/End, liquids and utility blocks).
   Preserve distinct target colors, alpha, face masks, rotations, state/model
   sharing and animation. A shared surface can generate several related paths,
   but only with an explicit recipe and review; never fill gaps by renaming or
   blindly upscaling vanilla pixels.
3. **Acquire and verify sources.** Use original procedural work and clearly
   licensed scans (for example CC0 sources already documented in
   `work/ASSET_CREDITS.md`). Record source URL, author, license, source-file hash
   and transformations for every input. Do not bundle Minecraft art or
   competitors' textures. If no appropriate legal source exists, create a
   physically plausible procedural material or leave a documented vanilla
   fallback rather than using an unlicensed substitute.
4. **Preserve the game contract.** Validate each output path, 256×256 default
   dimensions (plus optional 128/512 outputs), LabPBR channel semantics,
   alpha/cutout masks, animation `.mcmeta` and frames,
   connected-texture rules, path casing and deterministic ZIP contents. Do not
   replace block models, UVs, states or geometry as a shortcut. Per-face maps
   must remain aligned; preserve all shared-path relationships across stairs,
   slabs, walls, doors, panes and interactive states.
5. **Review in context and measure.** Generate contact sheets by material and
   block family, then check tiling, mip behavior, biome tint, cutout edges,
   animation and face orientation in Minecraft 26.3 with named shader/mod
   versions. Record actual hardware, settings and measured load time/FPS/VRAM
   before making performance claims. Structural tests are necessary but are not
   visual or runtime validation.
6. **Release in verified slices.** Publish independently testable material
   families and keep the vanilla fallback working. “Full support” is achieved
   only when the pinned 26.3 inventory has zero unexplained texture gaps, every
   exceptional sprite has a documented policy, and runtime checks pass—not when
   an arbitrary texture count is reached.

## Should this pack have its own shader?

**Not as the next implementation step.** Keep the pack shader-agnostic and
LabPBR 1.3-compatible while texture coverage and material calibration are still
in progress. Continue validating with established Iris-compatible LabPBR
shaders (currently the setup guide recommends Photon and also documents
Complementary Reimagined). This gives users a tested rendering path without
forcing them to install a project-specific renderer, and exposes material errors
across more than one shader implementation.

A custom shader could eventually be worthwhile as an **optional companion** if
real testing identifies pack-specific needs that existing shaders cannot meet:
for example, carefully controlled emission, restrained normal/height response,
consistent roughness interpretation, or a purpose-tuned profile for the target
GPU. It cannot make incomplete or inaccurate source textures realistic by
itself. It would also add a separate product surface: GLSL maintenance across
Minecraft/Iris versions, compatibility and licensing review, device/driver
coverage, settings and documentation, shader compilation failures, and an
ongoing performance budget on lower-end hardware. Shader-pack behavior is not
portable enough to assume one implementation works identically in Iris,
OptiFine and every LabPBR shader.

Recommended decision gates before starting a shader implementation:

- Finish representative texture families and obtain in-game screenshots and
  measurements on the stated target hardware.
- Reproduce a concrete visual or performance problem with at least two current
  LabPBR shaders, and verify that it is not a bad material map or setting.
- Prototype an optional Iris shaderpack (rather than modifying the generator or
  requiring a particular shader) with a short feature list, a low/medium/high
  profile, explicit LabPBR 1.3 behavior, graceful fallback and a version matrix.
- Compare its output and frame-time/VRAM cost to established shaders under the
  same scenes and settings. Do not claim it is “more realistic” without
  controlled visual review.

The sensible near-term work is therefore a complete, testable block inventory
and material roadmap—not a custom shader fork. Shader research can continue in
parallel, but a renderer should wait for evidence from a usable, broad material
set and actual Minecraft sessions.
